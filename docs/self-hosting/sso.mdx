title: "SSO"
description: "Let users sign in to GitArena with any OpenID Connect provider, such as Keycloak, Authentik, or GitLab, configured in the settings table."
---

GitArena supports single sign-on through OpenID Connect (OIDC). You can add any number of OIDC providers. Each provider is configured through a group of keys in the settings table.

<Warning>
  OAuth2 providers (GitHub, GitLab OAuth apps, and Bitbucket) are not supported yet. When you upgrade an instance that had GitHub, GitLab, or Bitbucket sign-in enabled, the database migration moves those credentials to `sso.oauth2.<provider>.client_id` and `sso.oauth2.<provider>.client_secret`. GitArena fails to start while any `sso.oauth2.*.client_id` key has a value. Clear those values to keep your instance running:

  ```sql
  UPDATE settings SET value = NULL WHERE key LIKE 'sso.oauth2.%.client_id';
  ```
</Warning>

## Settings keys

Every provider has a name that you choose, such as `keycloak`. The name appears in the provider's settings keys, its sign-in URL, and its login button.

| Key | Description |
|-----|-------------|
| `sso.oidc.<name>.client_id` | Client ID issued by the provider. GitArena loads the provider only when this has a value. |
| `sso.oidc.<name>.client_secret` | Client secret issued by the provider |
| `sso.oidc.<name>.issuer_url` | Issuer URL. GitArena discovers the provider's endpoints from it. |
| `sso.oidc.<name>.scopes` | Comma-separated scopes to request, e.g. `profile,email`. GitArena always requests `openid`. |

All four keys are required. GitArena fails to start if one of them is missing for a provider that has a `client_id`.

## Add an OIDC provider

<Steps>
  <Step title="Register GitArena with your provider">
    Create an OIDC client (sometimes called an application) in your identity provider. Use the authorization code flow and set the redirect URI to:

    ```text
    https://git.example.com/api/sso/<name>/authorize
    ```

    Replace `<name>` with the provider name you use in the settings keys. Copy the client ID, client secret, and issuer URL.
  </Step>
  <Step title="Add the provider to the settings table">
    The migrations do not create OIDC keys, so insert them:

    ```sql
    INSERT INTO settings (key, value, type) VALUES
      ('sso.oidc.keycloak.client_id',     'your_client_id',                          'string'),
      ('sso.oidc.keycloak.client_secret', 'your_client_secret',                      'string'),
      ('sso.oidc.keycloak.issuer_url',    'https://auth.example.com/realms/gitarena', 'string'),
      ('sso.oidc.keycloak.scopes',        'profile,email',                           'string');
    ```
  </Step>
  <Step title="Restart GitArena">
    GitArena loads SSO providers once at startup. After the restart, the login and registration pages show a button for the provider.
  </Step>
</Steps>

The login button uses the provider name. The names `github`, `gitlab`, and `bitbucket` get their brand label and icon. Any other name is shown capitalized with a key icon.

## How the sign-in flow works

When a user clicks a provider button:

<Steps>
  <Step title="Redirect to the provider">
    The browser goes to `/api/sso/<name>`, and GitArena redirects to the provider's authorization URL. The request uses PKCE and a nonce.
  </Step>
  <Step title="Handle the callback">
    The provider redirects back to `/api/sso/<name>/authorize` with an authorization code. GitArena exchanges the code for tokens and validates the ID token.
  </Step>
  <Step title="Resolve the account">
    If the provider account is already linked to a GitArena user, GitArena logs in that user. Otherwise, GitArena creates a new account when `allow_registrations` is `true`, and returns `403` when it is `false`.
  </Step>
  <Step title="Create the session">
    GitArena sets the `gitarena-session` cookie and redirects the user to `webauthn.origin`.
  </Step>
</Steps>

New accounts use the provider's `preferred_username` claim as the username. If that username is taken, GitArena appends a random suffix. The provider's email address becomes the primary email. GitArena marks it as verified when the provider's `email_verified` claim is `true`, and sends a verification email otherwise.

## Disabling a provider

Clear the provider's client ID and restart GitArena:

```sql
UPDATE settings SET value = NULL WHERE key = 'sso.oidc.keycloak.client_id';
```

The login button for that provider disappears after the restart. Existing accounts linked to that provider are not deleted.
